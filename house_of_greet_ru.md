# House of Greet

*Моим первым языком программирования был JavaScript,<br>
я изучал его по https://learn.javascript.ru<br>
В любой новой теме, будь это первая функция, первый метод класса, первый промис,<br>
был вывод приветствия через функцию sayHi()<br>
И мой "сценический псевдоним" так же основан на сигнатуре данной функции.<br>
В ходе техники House of Greet фейковый чанк "приветствует" аллокатор так,<br>
что тот принимает его за своего, не нарушая структуру двусвязного списка.*<br>

---
Концепт данной техники заключается в эксплуатации двусвязного списка **unsorted bin**,
что дает возможность **произвольной** аллокации в подконтрольной(-ых) для записи области(-ей) памяти и
**утечку** адреса unsorted_chunks из glibc с **восстановлением** циклического двусвязного списка unsorted bin

## 1. Техника существует для разных версий glibc в 2-х вариациях :

### 1.1. glibc <= 2.27 (большинство проверок отсутствуют - легкое исполнение, наибольшее влияние на память программы) :
	
- Наличие **Use-After-Free** для контроля поля bk чанка в unsorted bin (назовем этот чанк **victim_A**)
- Утечка кучи + знание адреса "фейкового" чанка (назовем его **evil**)
	
### 1.2. glibc > 2.27 (патч на проверки целостности кучи + чанка при его извлечении - дополнительные условия; влияние немного меньше но все равно значительное) :
	
- все перечисленное из пунка 1.
- размещение еще одного фейкового чанка на соответствующем расстоянии от **evil** с корректными полями **prev_size** & **size**	
- Наличие **Use-After-Free** для контроля поля **fd** еще одного чанка в unsorted bin (назовем этот чанк **victim_B**)
		
Как можно заметить, **полный импакт** наблюдается только в пункте 1. (можно выделить чанк вплоть до ~0х20000 байт).<br>В пункте 2. следствием этой атаки будет контроль **только над областью** начиная с адреса evil и заканчивая evil + размер evil'а, при условии **"честной"** линковки evil с unsorted_chunks через **UAF**.<br>
В добавок получаем **утечку** unsorted_chunks адреса, который кладется в qword по индексу 2, начиная с адреса **evil**.

## 2. Чтобы понять суть техники, детально рассмотрим работу аллокатора с unsorted bin в нашем контексте :

### 2.1. Пусть некоторые наши манипуляции с malloc/free (заполнение tcache/fastbin и/или добавление прослоек между чанками во избежании консолидации) привели unsorted bin в следующее состояние (в нем лежит 2 освобожденных чанка) :

```
На схеме стрелочки означают : "указывает на сам чанк; например bin через fd указывает на B, а не на поле fd внутри B, и B указывает своим bk на bin, а не на поле bk внутри bin"

					 _______________			 _______________			 _______________			 _______________
					|	   bin		|			|		B		|			|		A		|			|	   bin		|
					|_______________|			|_______________|			|_______________|			|_______________|
					|	   fd		|---------->|	   fd		|---------->|	   fd		|---------->|	   fd		|
					|_______________|			|_______________|			|_______________|			|_______________|
					|	   bk		|<----------|	   bk		|<----------|	   bk		|<----------|	   bk		|
					|_______________|			|_______________|			|_______________|			|_______________|
													голова						  хвост						
```

Где A - первый освобожденный чанк, а B - второй. Вставка в unsorted bin происходит в голову, а обход для извлечения начинается с хвоста.
	   
*Дамп памяти* :
	   
**Unsorted bin** :
```
	   		0x7ffff7e15b20: 0x0000555555559b80    		 		0x0000000000000000
			0x7ffff7e15b30: 0x0000555555559740 <== голова		0x0000555555559000 <== хвост
```				
**Чанк A** : 
```	   	
	   		0x555555559000: 0x0000000000000000 <== prev_size	0x0000000000000421 <== size | PREV_INUSE
			0x555555559010: 0x00007ffff7e15b20 <== fd			0x0000555555559740 <== bk
```			
**Чанк B**  :
```
			0x555555559740: 0x0000000000000000 <== prev_size	0x0000000000000421 <== size | PREV_INUSE
			0x555555559750: 0x0000555555559000 <== fd			0x00007ffff7e15b20 <== bk
```
### 2.2. Следующий malloc с соответствующим размером (при условиях что tcache и fastbin пусты для этого размера) вернет чанк A :
	
#### 2.2.1. Пусть запрошенный размер 0x410 байт, а размер чанка A == 0x420 байт (user data 0x410 + заголовок 0x10). Начинаем обход с хвоста :
		
```

					|_______________|			|_______________|			|_______________|			|_______________|
					|	   fd		|---------->|	   fd		|---------->|	   fd		|---------->|	   fd		|
```			

### 2.2.2. Аллокатор обрабатывает чанк A :
		  
#### 2.2.2.1. смотрит на поле size без учета флагов (сбрасывает биты PREV_INUSE / IS_MAPPED / NOT_MAIN_ARENA) - видит там 0x420
#### 2.2.2.2. считает конечный размер чанка запрошенного пользователем (аргумент malloc + 0x10 в качестве размера заголовка с полями size/prev_size) - получает 0x410 + 0x10 = 0x420 => чанк A подходит по размеру 
#### 2.2.2.3. в патче 2.28 проверяет целостность кучи и чанка A перед извлечением :
- **glibc >= 2.28** - Commit **b90ddd08f6dd688e651df9ee89ca3a69ff88cd0c** ("malloc: Additional
checks for unsorted bin integrity I.") :

```c
3733       if (__glibc_unlikely (chunksize_nomask (next) < 2 * SIZE_SZ)
3734               || __glibc_unlikely (chunksize_nomask (next) > av->system_mem))
3735             malloc_printerr ("malloc(): invalid next size (unsorted)");
3736           if (__glibc_unlikely ((prev_size (next) & ~(SIZE_BITS)) != size))
3737             malloc_printerr ("malloc(): mismatching next->prev_size (unsorted)");
3738           if (__glibc_unlikely (bck->fd != victim)
3739               || __glibc_unlikely (victim->fd != unsorted_chunks (av)))
3740             malloc_printerr ("malloc(): unsorted double linked list corrupted");
3741           if (__glibc_unlikely (prev_inuse (next)))
3742             malloc_printerr ("malloc(): invalid next->prev_inuse (unsorted)");
```
- На расстоянии **0x420** от чанка **A** должен находиться чанк с валидным размером (**size >= 0x10**) без флага **PREV_INUSE** и валидный **prev_size** (prev_size = **size** чанка **A**) :
```
		  			0x555555559000: 0x0000000000000000      							0x0000000000000421
					0x555555559010: 0x00007ffff7e15b20      							0x0000555555559740
						...
					0x555555559420: 0x0000000000000420 <== prev_size = size чанка A 	0x0000000000000300	<== валидный size без PREV_INUSE
```
- Проверка связности двусвязного списка - **A->bk->fd == A** & **A->fd == unsorted_chunks** :
```
					Если взглянуть на дамп чанков пункта 2.1., можно увидеть что целостность не нарушена, и по указателю bk, A ссылается на B, а тот, по fd, ссылается на A
```
#### 2.2.2.4. Делает извлечение чанка A и обновляет состояние двусвязного спика :

```c
3724       while ((victim = unsorted_chunks (av)->bk) != unsorted_chunks (av))
3725         {
3726           bck = victim->bk;
3727           size = chunksize (victim);
3728           mchunkptr next = chunk_at_offset (victim, size);
...			   /* код проверок, приведенный в 2.2.2.3. */
3783           unsorted_chunks (av)->bk = bck;
3784           bck->fd = unsorted_chunks (av);
...
```
> **2.2.2.4.1. bck = victim->bk;**<br>**bck** указывает на чанк идущий перед **A**. Это чанк **B**
		
> **2.2.2.4.2. unsorted_chunks (av);**<br>Он указывает на чанк идущий за **A**, т.к. в бине всего 2 чанка, и он закольцован на **адрес бина**, и **A** это **хвост**, то **fd A** указывает на **бин** (**unsorted_chunks (av)**)

> **2.2.2.4.3. unsorted_chunks (av)->bk = bck;**<br>т.к. чанк **A** извлечен, и т.к. **A** был **хвостом**, то нужно обновить **хвост**.<br>Если заметить что **адрес бина** на **0х10** меньше адреса в памяти где хранятся **голова** и **хвост** (см пункт **2.1.**), то **unsorted_chunks (av)->bk = bck** точно попадает в **хвост**

> **2.2.2.4.4. bck->fd = unsorted_chunks (av);**<br>В итоге чанк **B** указывает на **бин**. Теперь логически чанк **А** извлечен
	
> **2.2.2.4.5.** Делает дальнейшие преобразования кучи и **адрес чанка A** возвращается через следующий **malloc**

# Итоги
Как мы уже обсудили, на **glibc** версий <= **2.27** эта техника достаточно **легка** в исполнении (нужны лишь **утечка кучи** и **UAF** для одного чанка), позволяющая осуществить свободный **arbitrary alloc** + **утечку** unsorted_chunks. На версиях **glibc** >= **2.28**, был внесен **критический** патч, который ограничивает такую свободу, но не делает **House of Greet** невозможной; отличия в условиях - наличие UAF для **второго чанка**, и более **детальная** подготовка подконтрольной(-ых) для записи области(-ей) памяти. Не смотря на более простые техники в связке с UAF, такие как **tcache poisoning**, **fastbin dup**, **tcache stashing unlink** etc., **House of Greet** позволяет получить область памяти, которая **перекрывает** промежуточные данные, что в некоторых кейсах может быть полезно. Особенно учитывая **сохранение** целостности unsorted bin'а после атаки, что позволяет **продолжить** цепочку эксплуатации.
